# ERC-777 商业案例讲解

**一句话**：ERC-777 曾试图在「转账时自动通知收款合约」，方便订阅、分红、钱包即服务等 **自动化商业流程**；但因 **安全与生态** 原因，近年新项目极少采用。本文以 **商业史与教训** 为主，课内代码仅作机制演示（`erc-demo/erc777/`）。

---

## 1. 设计时的商业愿景

| 愿景 | 777 的机制 | 对标 Web2 |
|------|------------|-----------|
| 转账即开通服务 | 接收方合约实现 `tokensReceived` 自动记账 | 支付成功回调 webhook |
| 运营商代扣 | `operator` 经用户授权后代转 | 免密代扣、委托扣款 |
| 统一「发送」接口 | `send` 替代 transfer + 回调 | 支付网关统一 API |

对 **SaaS、会员续费、分账** 类产品，听起来可减少「先充值到合约再 activate」的两步流程。

---

## 2. 历史上曾出现的业态（与现状）

### 2.1 代币发售与实验性项目

- 2018–2020 年部分 **ICO / IEO 代币** 选用 777 以强调「高级代币标准」。  
- **现状**：主流交易所与钱包优先支持 ERC-20；777 流动性差，**上市与集成成本高**，商业上已不划算。

### 2.2 与企业结算的误读

- 银行链（如 **JPM Coin**）多为许可链上的定制标准，**并非** 公开链上的 ERC-777。  
- **启示**：企业要的是合规 + 冻结 + 审计，不是公开链上的通用 Hook 代币。

### 2.3 与 ERC-1820 注册表

- 777 依赖 **ERC-1820** 查询「某地址是否实现了接收接口」。  
- **商业影响**：多一层基础设施依赖；若注册表或实现有误，资金可能进「无法处理」的合约。

---

## 3. 为何商业上被 ERC-20 生态取代

| 因素 | 对商业的影响 |
|------|----------------|
| **重入与恶意 Hook** | 接收合约在转账中执行任意逻辑 → 交易所、托管方不愿默认支持，**上架慢** |
| **与 ERC-20 不兼容** | 大量 DeFi 只认 `transfer` / `approve`，777 需桥接或包装，**流动性碎片化** |
| **审计与保险成本** | 协议承保、交易所风控清单常排除小众标准 → **合作门槛高** |
| **OpenZeppelin 等弃用** | 开发供应链不再默认提供 777 → 人力与维护成本上升 |

**行业共识（2024 起）**：新业务用 **ERC-20 + 显式存款函数**（如 `deposit()` 回调用户标签），或 **账户抽象** 做自动化，而不是 777 Hook。

---

## 4. 仍可从 777 学到的商业模型（换实现方式）

| 777 想做的生意 | 今天更常见的做法 |
|----------------|------------------|
| 订阅扣款 | 链下 Stripe + 链上周期性 `transferFrom`（需用户 approve）或智能账户 |
| 分红 | Merkle 空投、claim 合约、或链下计算 + 批量 transfer |
| 钱包即服务 | 4337 Paymaster、CEX 内部账本 |

课内 **`ERC777Vault`**：演示「钱打进金库合约即更新内部账本」——商业上等价于 **用户主动调用 deposit()** 或 **支付通道**，更安全可控。

---

## 5. 决策建议（给产品 / 商务）

- **新项目发币**：选 **ERC-20**（或合规许可链方案），不要选 777。  
- **收购/尽调旧项目**：若资产是 777，要问清交易所支持与合约审计结论。  
- **学习目的**：读 777 是为理解「为什么 DeFi 不喜欢转账中回调」，而非为了上线。
