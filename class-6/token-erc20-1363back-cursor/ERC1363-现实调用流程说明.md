# ERC1363 现实调用流程说明（基于当前代码）

本文说明以下 2 个合约在真实使用中的调用链路与目的：

- `ERC1363Token.sol`
- `TokenBank1363.sol`

---

## 1. 部署阶段（一次性）

### 第 1 步：部署 `ERC1363Token`

**发生了什么**

- 执行 `constructor() ERC20("CallbackToken", "CBT")`
- `_mint(msg.sender, INITIAL_SUPPLY)` 把初始总量铸造给部署者

**目的**

- 创建可流通的 ERC20 代币
- 让部署者拿到初始余额，后续可分发给用户

---

### 第 2 步：部署 `TokenBank1363(tokenAddress)`

**发生了什么**

- 构造函数校验 `tokenAddress != address(0)`
- 保存 `token = IERC20(tokenAddress)`

**目的**

- 把“银行”绑定到唯一受支持的 token 合约
- 避免后续任意 token 都能触发存款回调

---

## 2. 存款流程（核心：transferAndCall）

假设用户希望把 100 个 `CBT` 存入银行。

### 第 1 步：用户调用 token 合约

用户调用：

```solidity
token.transferAndCall(bankAddress, 100 ether, data)
```

**目的**

- 在一笔交易里完成“转账 + 通知接收方”
- 不需要用户再额外手动调用银行的 `deposit`

---

### 第 2 步：`ERC1363Token.transferAndCall` 内部先转账

代码行为：

- `_transfer(_msgSender(), to, value)`

**目的**

- 先把代币余额真实转到银行合约地址
- 保证回调执行时，资金状态已经是“已到账”

---

### 第 3 步：token 合约主动回调接收方

代码行为：

- `_checkOnTransferReceived(...)`
- 内部调用 `IERC1363Receiver(to).onTransferReceived(operator, from, value, data)`

**目的**

- 告诉接收方合约：“有一笔 token 已转给你，请你按业务记账/处理”
- 把 `from/value/data` 这类业务上下文传过去

---

### 第 4 步：银行合约处理回调并记账

`TokenBank1363.onTransferReceived` 中：

- `require(msg.sender == address(token))`：只接受指定 token 的回调
- `require(from != address(0))`、`require(value > 0)`：参数有效性校验
- `deposits[from] += value`：给用户增加存款余额
- `emit Deposited(from, value)`：发事件，便于前端和索引器追踪

**目的**

- 防伪造：避免外部地址伪造“存款成功”
- 建立银行内部账本（`deposits`）
- 可观测：链上日志可追踪

---

### 第 5 步：回调返回 magic value（selector）

银行返回：

```solidity
return IERC1363Receiver.onTransferReceived.selector;
```

token 合约检查：

```solidity
retval == IERC1363Receiver.onTransferReceived.selector
```

**目的**

- 双方按 ERC1363 约定完成“握手确认”
- 表示接收方明确接受了这笔回调

> 注意：这不是在对比 `data` 内容，而是在校验回调返回值是否符合协议。

---

### 第 6 步：任一步失败则整笔交易回滚

如果出现以下任一情况：

- `to` 不是合约地址
- 回调函数 `revert`
- 返回值不是约定 selector
- 银行内部校验失败（例如 token 不匹配）

都会导致交易回滚，用户余额和银行记账都恢复到交易前状态。

**目的**

- 保证原子性（要么全部成功，要么全部失败）
- 防止“转账成功但业务记账失败”的状态不一致

---

## 3. 提款流程（withdraw）

用户调用：

```solidity
bank.withdraw(amount)
```

### 第 1 步：参数与余额校验

- `amount > 0`
- `deposits[msg.sender] >= amount`

**目的**

- 防止无效调用与超额提现

### 第 2 步：先扣账，再转账

- `deposits[msg.sender] -= amount`
- `token.transfer(msg.sender, amount)`

**目的**

- 遵循“Checks-Effects-Interactions”思路
- 先更新内部状态，再与外部合约交互，降低重入风险

### 第 3 步：发出 `Withdrawn` 事件

**目的**

- 让前端/监控系统可追踪提现行为

---

## 4. 现实中的典型时序（简版）

1. 用户钱包发起 `transferAndCall(bank, amount, data)`
2. token 合约扣用户余额并给银行地址加余额
3. token 合约调用银行 `onTransferReceived(...)`
4. 银行校验调用来源、参数并写入 `deposits[user]`
5. 银行返回 selector
6. token 合约校验 selector 正确，交易成功
7. 用户未来可调用 `withdraw` 取回 token

---

## 5. 这套设计在现实中的价值

- **一笔交易完成存款**：比“先 transfer 再单独 deposit”更顺滑
- **强一致性**：转账与记账原子化，失败自动回滚
- **协议可组合**：任何实现了 `IERC1363Receiver` 的合约都可接入
- **对前端友好**：通过事件可构建清晰的存取款历史
