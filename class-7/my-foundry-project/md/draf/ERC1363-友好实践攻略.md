# ERC1363 友好实践攻略（结合本仓库示例）

面向：**刚学完基础 Solidity、已能把简单合约部署到测试网**的同学。  
你**不必先「从零写标准」**——先理解它在做什么、怎么在本项目里**跑通、再动手改**，会轻松很多。

## 一、先用一句话理解 ERC1363

普通 **ERC-20**：你调用 `transfer`，代币到账，**故事结束**。

**ERC-1363**（常见叫法）：在 **`transfer` / `transferFrom` / `approve` 的同一条交易里**，多走一步——**让「合约地址」再执行一段你约定的回调**。这样收款方或支出方可以**在同一笔交易里**记账、触发业务逻辑，而不必让用户再发第二笔交易去「通知」合约。

可以把它想成：**「转账 + 按门铃」**：门铃就是 `onTransferReceived` / `onApprovalReceived`。

> 正式规范见 [EIP-1363](https://eips.ethereum.org/EIPS/eip-1363)。本仓库实现的是其中**最常用**的几条路径，接口写在 `src/IERC1363*.sol`，便于对照阅读。

## 三、三条常用路径（和 ERC-20 对比）

1. **`transferAndCall(to, value[, data])`**  
   - 像 `transfer`，但 `to` **必须是合约**，且会调用 `to.onTransferReceived(...)`。  
   - `data` 可传任意字节，给接收方做「附言」（例如区分业务类型）。

2. **`transferFromAndCall(from, to, value, data)`**  
   - 像 `transferFrom`（先消耗 `from` 给调用者的 allowance），再对 `to` 做同样的回调。  
   - 适合「操作者帮用户把代币送进某个合约并触发逻辑」的场景。

3. **`approveAndCall(spender, value, data)`**  
   - 先 `approve(spender, value)`，再立刻调用 `spender.onApprovalReceived(...)`。  
   - 适合「授权 + 让支出方在同一笔交易里登记或拉款」的流程（具体是否拉款取决于支出方回调里写什么；本课 `CallbackReceiverDemo` 里留了 `pullFrom` 示例）。

本仓库的代币在回调里会检查：

- 收款地址 **必须是合约**（不能是普通钱包地址），否则会 `revert("ERC1363: transfer to non-contract")`；  
- `approveAndCall` 的 `spender` 也 **必须是合约**，否则 `revert("ERC1363: approve to non-contract")`。

这是**刻意设计**，避免对 EOA 做无意义的 `call`。测试文件里也有对应例子。

### 第 0 步：能编译、能跑测试

在项目根目录：

```bash
cd /Users/evan/web3Code/learn-chain-class-demo/class-7/my-foundry-project
forge build
forge test --match-contract Token10000WithCallbacksTest -vv
```

看到绿色 `PASS`，说明你对「转账回调 / 授权回调 / EOA 会失败」有了**可运行**的参照。改代码后可以反复跑同一组测试。

### 第 1 步：只读代码，对照测试画「时间线」

拿 `test_transferAndCall_toContract_invokesCallback` 想一遍顺序：

1. 测试合约（当作用户）持有全部 `CTT`；  
2. 调用 `transferAndCall(接收合约, 金额, 0x01)`；  
3. 代币先完成内部转账，再 `call` 接收合约的 `onTransferReceived`；  
4. 接收合约 `emit` 事件并返回规定的 **4 字节魔数**（接口里要求的 `selector`）。

若返回不对，代币会 `revert("ERC1363: bad onTransferReceived")`——这是规范里「让调用方立刻知道对接错了」的方式。

### 第 2 步：本地链上玩一遍（和测试网一样要「真实地址」）

用 `anvil` + `DeployAll`（或你自己写只部署代币 + `CallbackReceiverDemo` 的脚本），拿 `cast` 发交易。要点：

- `transferAndCall` 的第三个参数是 `bytes`：空附件写 `0x`，有附件写 `0x0102` 这种十六进制。  
- 收款地址填 **`CallbackReceiverDemo` 部署出来的地址**，不要填自己的 MetaMask 地址（否则按本实现会 `revert`）。

具体 `cast` 参数可抄测试里的数值（例如 `10 * 10**18`  wei）再换成你的地址。RPC 用本地或 Sepolia 均可，与 `--rpc-url` 一致即可。

### 第 3 步：Sepolia 上实践（你已会部署的前提下）

1. 按 `md/history/部署说明与操作手册.md` 部署 **`Token10000WithCallbacks`** 与 **`CallbackReceiverDemo`**（例如 `DeployAll`）。  
2. 用**持有代币的账户**对代币合约调用 `transferAndCall(demo地址, 数额, 0x)`。  
3. 在 [Sepolia Etherscan](https://sepolia.etherscan.io/) 打开交易，看 **Internal Tx** 或合约 **Logs**，确认 `TransferCallback` 等事件是否出现。

这样你就完成了一条「和课内测试等价、但发生在测试网」的闭环。

### 第 4 步（进阶）：自己改一点点

在**拷贝** `CallbackReceiverDemo` 的前提下尝试：

- 在 `onTransferReceived` 里根据 `data` 的第一个字节分支 `emit` 不同事件；  
- 或暂时写错返回值，看测试/链上是否按预期 `revert`。

改小步、每步跑测试，比一上来写生产级合约更稳。

## 五、实践时的「最佳实践」（初学版 checklist）

1. **回调里尽量简单**  
   先 `emit`、改自己的存储；避免在回调里再调用未知第三方或复杂外部调用，否则 Gas 与**重入**风险都会上升。

2. **牢记调用顺序**  
   本课代币是：**先完成转账或授权，再调用你的回调**。此时余额或 allowance 已经更新；若在回调里再次进入代币逻辑，要想清楚是否构成重入（与「检查-生效-交互」模式对照）。

3. **返回值必须对**  
   `onTransferReceived` / `onApprovalReceived` 必须返回接口规定的 **bytes4**（代码里已用 `...selector` 写法，照着抄即可）。错了代币会直接 `revert`。

4. **明确「仅合约」约束**  
   本实现禁止对 EOA 使用 `transferAndCall` / `approveAndCall`。若你的产品需要「钱包也能收」，应走普通 `transfer`，或换用别的标准/自定义流程，而不是强行 `call` EOA。

5. **文档与前端提示**  
   若你对外提供合约：在 README 或前端写清楚「请用 `transferAndCall` 并填接收合约地址」，能减少用户误操作。

6. **先测试网、再主网**  
   涉及资金路径时，用多账户、小额度跑通 `approveAndCall` + `pullFrom` 这类组合，再在主网缩小权限与额度。

7. **与「普通 ERC-20」并存**  
   OpenZeppelin 的 `ERC20` 仍可用：`transfer` / `approve` 不受影响。1363 风格函数是**额外入口**，便于「一步完成多步语义」的场景。
