## 二、链上代币：脑子里先放什么模型

可以想象成：**某一份智能合约里有一份公开账本**，记录了「每个地址」在这种代币下「还有多少」。

- **不是**把文件发到对方邮箱；**而是**合约存储里的数字被改掉：你少、对方多。  
- 你的钱包**不「装」代币文件**；钱包保存密钥，你用它**签名交易**，去**调用代币合约**的函数，从而改那份账本。  
- 后面说的 **ERC-20** 与 **ERC-1363**，都是在约定：**账本怎么读、交易怎么写**。

## 三、ERC-20：从「用户怎么用」到「每个参数是谁」

**同质化**：每一枚代币一样（像同一种积分点），不搞「每张 NFT 都不同」。

### 3.1 白话版三件大事 + 生活类比

1. **我有多少**：`balanceOf(我的地址)`  
2. **我直接转给别人**：`transfer(对方地址, 数量)`  
3. **我允许某个合约替我花**：先 `approve(合约地址, 允许上限)`，再由该合约（作为 `msg.sender`）`transferFrom(我, 最终收款方, 数量)`  

第 3 条就是 DApp 里常说的「授权」。没有授权，别人的合约不能随便从你账上划代币。

| 链上概念 | 可以粗略理解成 |
|----------|----------------|
| `transfer` | 我直接扫码转你钱。 |
| `approve` + `transferFrom` | 我给商家「代扣额度」，商家在额度内从我账户划走。 |

### 3.2 最小函数表（认识名字即可）

| 函数（常见） | 作用（一句话） |
|--------------|----------------|
| `name` / `symbol` / `decimals` | 人类可读的名字、符号、**小数位数**（见下节）。 |
| `totalSupply` | 这种代币一共发行了多少（最小单位计）。 |
| `balanceOf` | 某个地址余额（最小单位计）。 |
| `transfer` | 从 **`msg.sender`** 转给参数 `to`。 |
| `approve` | **`msg.sender`** 授权 `spender` 代扣上限。 |
| `allowance` | 查某 owner 对某 spender 还剩多少代扣额度。 |
| `transferFrom` | **被授权方**（当前 `msg.sender`）从 `from` 转给 `to`。 |

### 3.3 `decimals`：钱包里的「1 枚」和链上的 `amount`

- 合约里记账、转账用的 `amount` 几乎都是 **整数**，单位叫 **「最小单位」**（类似 1 ETH = 10¹⁸ wei）。  
- **`decimals`**（常见为 `6` 或 `18`）表示「1 个展示用的代币」等于多少个最小单位：  
  - `decimals == 18` 时，界面展示 1 枚，链上数量常为 `10**18`（个最小单位，与 1 ETH = 1e18 wei 同理）。  
- 钱包界面把最小单位除以 `10 ** decimals` 给你看「几位小数的人类读数」。  
- **初学易错**：在脚本里手填 `100` 想转「100 枚」，若小数 18，链上应接近 **`100 * 10**18`**；少写位数会只转极小一笔。

### 3.4 「币都在一个合约里」：账本在哪、怎么到用户、用户怎么用

**分清两层含义：**

1. **账本存在哪**：所有地址的余额，都存在 **这一份 ERC-20 合约** 的存储里（例如 `mapping(address => uint256) balanceOf`）。  
2. **是不是字面「币堆在合约地址里」**：**不是**。没有往合约「搬箱子」，只有 **每个地址一行数字**。发行常见写法是 `_mint(部署者, 总量)`，即 **部署者名下那一行 = 总量**。

**分给用户**：部署者（或任何有余额的人）对用户发起 **`transfer(用户地址, 数量)`** → 部署者那行减少，用户那行增加。用户钱包显示的余额来自读 **`balanceOf(用户地址)`**。

**用户平常怎么用（操作视角）：**

1. 拿到 **代币合约地址**。  
2. 钱包「添加代币」：读 `balanceOf`、`symbol`、`decimals` 等并展示。  
3. **点对点转账**：你发起 `transfer(对方, 数量)`，此时 **`msg.sender` 即你**。  
4. **给 DApp 用**：界面里「授权」→ `approve(协议, 额度)`；协议再 `transferFrom` 划走你的代币。

### 3.5 `msg.sender` 是谁？与各函数入参「到底是谁」

- 你用 MetaMask 对 **代币合约** 调 `transfer`：代码在代币里跑，**`msg.sender` = 你的 EOA**（不是代币合约地址）。  
- 代币合约自己在代码里用 **`address(this)`**；它改 `mapping`，**不会**因此变成 `msg.sender`。  
- **DEX 路由** 代你调 `transferFrom` 时：**`msg.sender` = 路由合约**；能划走你的币是因为你 **`approve` 过该路由**。

#### `transfer(address to, uint256 amount)`

| 参与方 | 是谁 |
|--------|------|
| 从谁的余额扣 | **`msg.sender`** |
| `to` | 接收方（EOA 或合约） |
| `amount` | **最小单位**数量 |

#### `approve(address spender, uint256 amount)`

| 参与方 | 是谁 |
|--------|------|
| 授权人 | **`msg.sender`** |
| `spender` | 被允许代扣的地址（**多为合约**） |
| `amount` | 授权上限 |

#### `transferFrom(address from, address to, uint256 amount)`

| 参与方 | 是谁 |
|--------|------|
| 谁有资格调用 | **`msg.sender` 须为 `from` 已 approve 的 `spender`** |
| `from` | 被扣余额的人（**不必**等于 `msg.sender`） |
| `to` | 最终收款方 |
| `amount` | 划转数量（最小单位） |

#### `balanceOf` / `allowance`

括号里的地址是**账本角色**；只读调用与「谁发起查询」无必然关系。

### 3.6 事件：`Transfer` 与 `Approval`（浏览器里那一串串日志）

ERC-20 约定在余额/授权变化时 **`emit` 事件**（链上日志），方便：

- **区块浏览器**（如 Etherscan）展示「从谁到谁」；  
- **索引器 / 后端** 监听某代币的转账，做统计、对账、充值到账检测。

初学只需知道：**转账成功几乎总伴随 `Transfer`；`approve` 会伴随 `Approval`**。你在测试网点开一笔交易的 **Logs** 标签即可看到。

### 3.7 常见坑（提前知道少交学费）

| 坑 | 说明 |
|----|------|
| **小数位搞错** | 链上 `amount` 按最小单位；和界面「1 枚」差 `10**decimals` 倍。 |
| **转错地址** | 链上不可撤销；转给不认识地址几乎无法找回。 |
| **把代币 `transfer` 进「没有提现逻辑」的合约** | 合约余额数字在，但若**没有**对外暴露 `transfer` 再转出的函数，可能**永远锁死**（除非升级/特殊救援）。给合约充值前先看它是否支持「存款」路径。 |
| **授权给不信任合约 / 无限额度** | `approve(spender, type(uint256).max)` 省事但有风险；恶意或漏洞合约可一次划走大额。只授权**可信合约**、**够用额度**，用完可 `approve(spender, 0)` 收回（视产品是否支持）。 |
| **approve 竞态**（了解即可） | 从 `N` 改到 `M` 时，若旧 spender 抢跑，在部分模型下有历史讨论；产品侧常用「先 0 再新值」或改用更安全模式。 |

### 3.8 ERC-20 的「边界」（为什么还要有 ERC-1363）

普通 `transfer` 完成后，**接收方若是合约，也不会自动执行你的业务逻辑**。  
你只是改了他的 `balanceOf`，他未必知道「这笔钱对应哪笔订单」——除非你再发交易调他的函数，或靠索引器对 **`Transfer` 事件** 做链下/链上业务对账。

**ERC-1363 想解决的**：在**同一笔交易**里，完成「改账本 + 通知对方合约执行约定回调」。

## 四、ERC-1363：在 ERC-20 之上加「转账/授权 + 回调」

### 4.1 一句话

在 ERC-20 已覆盖的转账/授权之外，约定如 **`transferAndCall` / `approveAndCall`**：代币合约在**改完账本后**，立刻 **`call`** 对方合约的固定函数（如 `onTransferReceived`），使对方**同一笔交易内**记账或继续业务流程。

### 4.2 与 ERC-20 的关系

- **不取代** ERC-20；常见实现是 **ERC-20 + 额外入口**。  
- 仍可用 `transfer` / `approve` / `transferFrom`。  
- 需要「一步：到账 + 对方合约动起来」时，再考虑带 `AndCall` 的路径。

### 4.3 两个回调角色（本仓库接口名）

| 接口 | 谁实现？ | 何时被代币调用？ |
|------|----------|------------------|
| `IERC1363Receiver.onTransferReceived` | **接收代币的合约** | 转入该合约且余额已更新之后。 |
| `IERC1363Spender.onApprovalReceived` | **被授权的支出方合约** | 授权给它之后。 |

回调须返回约定 **`bytes4`**，否则代币常 `revert`（接口契约）。

### 4.4 本仓库对照文件

| 文件 | 作用 |
|------|------|
| `src/IERC1363.sol` | 扩展函数形状。 |
| `src/Token10000WithCallbacks.sol` | 教学用代币实现。 |
| `src/CallbackReceiverDemo.sol` | 接收/支出回调 + 事件，便于观察。 |
| `test/Token10000WithCallbacks.t.sol` | **推荐第一个阅读入口**。 |

本课实现里部分 API **要求对方为合约**；对 EOA 会 `revert`，属刻意约束。细节见 **`ERC1363-友好实践攻略.md`**。

## 五、并排对照：我到底该记住什么？

| 维度 | ERC-20 | ERC-1363（常见用法） |
|------|--------|----------------------|
| 核心问题 | 余额与授权怎么变 | 同上 + **对方合约要立即反应** |
| 典型调用 | `transfer` / `approve` + `transferFrom` | `transferAndCall` / `approveAndCall` 等 |
| 对用户 | 最常见 | 特定 DApp 或课内示例 |
| 原子性（直觉） | 一步 = 改账本 | 一步 ≈ **改账本 + 调用对方** |

## 七、小白常见疑惑（FAQ）

**Q：`transfer` 里的 `msg.sender` 是代币合约还是我的钱包？**  
A：你用钱包发起时，**`msg.sender` 是你的 EOA**（若经中间合约代发，则是该合约）。代币合约是**被调用方**。

**Q：钱包里的「币」存在哪？**  
A：存在代币合约的存储里，记在 **`balanceOf(你的地址)`** 这一行；钱包只是读链展示。

**Q：`transferAndCall` 比 `transfer` 更省 Gas 吗？**  
A：一般 **更贵**（多一次对方合约执行）；省的是**用户少发一笔交易、少一次交互**的产品成本，要整体权衡。

**Q：必须先学 ERC-1363 吗？**  
A：**不必**。先稳 ERC-20 + 会读事件 + 会看浏览器交易，再学 1363 更顺。

**Q：所有代币都支持 `transferAndCall` 吗？**  
A：**不是**。USDT/USDC 等常见币**未必**实现；以该代币合约源码为准。

## 九、小结

- **ERC-20**：同质化代币的公共账本——**`amount` 多为最小单位**；**`transfer` 从 `msg.sender` 扣**；**`approve` + `transferFrom`** 支撑协议代扣；**事件**便于浏览器与索引；注意**小数、地址、授权、误转合约**等坑。  
- **ERC-1363**：在 20 之上，用 **转账/授权 + 回调** 把资产动作与对方合约逻辑尽量绑在**同一笔交易**。  
- **入门最短路径**：先读懂 **§三** 与 **`Token10000WithCallbacks.t.sol`**，再跑测试、可选上 Sepolia 看 **Logs**。

祝学习顺利：先跑通，再读规范；先改小 demo，再碰主网与大额。
